# Contributing to OrcheStore

Thank you for your interest in contributing to OrcheStore.

## Philosophy

OrcheStore aims to simplify and automate state management patterns commonly found in the React, Redux, and TypeScript ecosystem.

The project is built around a simple idea:

> Developers should spend less time wiring state management infrastructure and more time building application features.

Contributions should help make state management:

- Simpler
- More intuitive
- More maintainable
- More scalable
- Less repetitive
- Strongly typed by default

New features and improvements should reduce friction, improve developer experience, or eliminate common sources of boilerplate and complexity.

## Before Contributing

Before opening an issue or pull request:

- Search existing issues and discussions.
- Review the current documentation.
- Verify that the issue or proposal has not already been addressed.

## Reporting Bugs

When reporting a bug, please include:

- OrcheStore version
- React version
- Redux Toolkit version
- Environment details
- Reproduction steps
- Expected behavior
- Actual behavior

Providing a minimal reproducible example is highly appreciated.

## Suggesting Features

Feature requests should clearly explain:

- The problem being solved
- Why the current API is insufficient
- The proposed solution
- Potential trade-offs or limitations

Features that increase complexity without providing substantial value may not align with the project's goals.

## Pull Requests

Pull requests should be focused, well-described, and limited to a single concern whenever possible.

Please:

- Follow the existing code style and conventions
- Keep public APIs consistent with the project's design philosophy
- Update documentation when introducing or modifying public APIs
- Avoid unrelated refactoring
- Include examples when adding new functionality

## Design Principles

When contributing to OrcheStore, prioritize:

- Simplicity over cleverness
- Developer experience over ceremony
- Strong TypeScript inference
- Predictable behavior
- Clear and discoverable APIs
- Centralized business logic
- Minimal boilerplate

Avoid introducing abstractions that make the library harder to understand, maintain, or adopt.

## Documentation

Documentation is an important part of every contribution.

Changes that affect public APIs, runtime behavior, or developer workflows should include corresponding documentation updates.

Documentation should be:

- Clear
- Concise
- Example-driven
- Consistent with existing terminology

## Questions and Discussions

If you are unsure about an implementation, API design, or architectural direction, consider opening an issue or discussion before starting significant work.

Early feedback helps keep the project aligned with its goals and avoids unnecessary effort.

## Code of Conduct

By participating in this project, you agree to interact respectfully and constructively with other contributors and community members.

## Thank You

Every contribution, whether it is a bug report, documentation improvement, feature proposal, or code contribution, helps improve OrcheStore and is greatly appreciated.
